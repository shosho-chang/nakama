**1 — CODE GROUNDING**

ADR-043 is broadly right about the current write paths, but a few details need tightening before it can be treated as implementation guidance.

`KB/Wiki/Concepts/` is indeed the current LLM-written concept target in code. Route C calls `_execute_plan`, then `_execute_concept_action`, then `kb_writer.upsert_concept_page(...)` in [agents/robin/ingest.py](E:/nakama-adr043-centaur/agents/robin/ingest.py:467). The writer hard-codes `KB/Wiki/Concepts/{slug}.md`, uses `_DIFF_MERGE_PROMPT`, and calls `shared.llm.ask(... model="claude-opus-4-7", max_tokens=16000)` in [shared/kb_writer.py](E:/nakama-adr043-centaur/shared/kb_writer.py:43), [shared/kb_writer.py](E:/nakama-adr043-centaur/shared/kb_writer.py:113), and [shared/kb_writer.py](E:/nakama-adr043-centaur/shared/kb_writer.py:145). So the ADR’s “LLM auto-written Opus diff-merge” claim is correct.

Book promotion B is gated. `promotion_wiring.py` only supports `dry_run`; `llm` mode raises `RuntimeError("LLM mode not yet wired...")` in [thousand_sunny/promotion_wiring.py](E:/nakama-adr043-centaur/thousand_sunny/promotion_wiring.py:174). Current `main` contains no merged `LlmClaimExtractor`; the `feat/n519-llm-promotion-extractor` branch exists but is not in this worktree. ADR-043 should keep saying “planned / branch-local,” not “available.”

Video E needs one correction. `shared/video_source_map_builder.py` produces exactly one `SourcePageReviewItem` and no concept review items, as its docstring and return path show in [shared/video_source_map_builder.py](E:/nakama-adr043-centaur/shared/video_source_map_builder.py:1) and [shared/video_source_map_builder.py](E:/nakama-adr043-centaur/shared/video_source_map_builder.py:228). But the service layer can still produce video `EntityReviewItem`s for speaker chips; it bypasses the concept engine, not all non-source promotion behavior, in [shared/promotion_review_service.py](E:/nakama-adr043-centaur/shared/promotion_review_service.py:349). Phrase this as “video has source-page plus entity chips, but no concept candidate path.”

The “does not exist yet” claim is mostly true only against the live vault, not the repo. The repo has no `KB/` tree. In the configured vault, `KB/Permanent`, `KB/Wiki/MOCs`, and `KB/Fleeting` do not exist. However, `KB/Wiki/Concepts` exists and currently contains zero markdown files. That makes any “bulk demote existing concept pages” step stale or no-op today. ADR-043 should not imply there is a large existing C concept corpus waiting to be marked `status: candidate`.

The ADR also under-specifies all schema and renderer consequences. `ConceptPageV2` has no `status` field and is strict (`extra="forbid"`) in [shared/schemas/kb.py](E:/nakama-adr043-centaur/shared/schemas/kb.py:91). `promotion_renderer.render_concept_page` still emits `type: concept`, not `status: candidate`, in [shared/promotion_renderer.py](E:/nakama-adr043-centaur/shared/promotion_renderer.py:218). `promotion_targets.resolve_target_path` only understands source, concept, and entity review items, and concept target resolution assumes canonical concept paths in [shared/promotion_targets.py](E:/nakama-adr043-centaur/shared/promotion_targets.py:34). ADR-043’s candidate layer is a semantic design, not implemented behavior.

**2 — DRIFT DETECTION**

ADR-043 intentionally supersedes parts of ADR-024 and ADR-011, but it needs sharper supersession boundaries.

ADR-024 defines “Global KB Concept” as the long-term page under `KB/Wiki/Concepts` and describes promotion review as writing formal `KB/Wiki` pages after human approval in [docs/decisions/ADR-024-source-promotion-and-reading-context-package.md](E:/nakama-adr043-centaur/docs/decisions/ADR-024-source-promotion-and-reading-context-package.md:36). ADR-043 changes that meaning: `KB/Wiki/Concepts` becomes AI candidate/reference material, while `KB/Permanent` becomes the human-owned knowledge layer. That is not a minor rename. It invalidates ADR-024 vocabulary and should be stated as an amendment to the term “Global KB Concept,” not just a layout addition.

ADR-011 also conflicts. Its core model is a cross-source evidence aggregator concept page, with `create`, `update_merge`, `update_conflict`, and `noop` actions documented in [docs/decisions/ADR-011-textbook-ingest-v2.md](E:/nakama-adr043-centaur/docs/decisions/ADR-011-textbook-ingest-v2.md:40) and [docs/decisions/ADR-011-textbook-ingest-v2.md](E:/nakama-adr043-centaur/docs/decisions/ADR-011-textbook-ingest-v2.md:301). ADR-043 should not pretend that adding `status: candidate` is a small metadata tweak. It changes the epistemic role of these files from “KB concept page” to “machine-generated prompt fodder.”

ADR-028 and `VAULT-LAYOUT.md` create a bigger ownership issue. `KB/` is currently documented as Agent-only in [docs/VAULT-LAYOUT.md](E:/nakama-adr043-centaur/docs/VAULT-LAYOUT.md:115). `KB/Wiki/Concepts` is documented with producers and consumers including `kb_writer`, annotation merger, `kb_search`, Brook synthesize, and Reading Context Package in [docs/VAULT-LAYOUT.md](E:/nakama-adr043-centaur/docs/VAULT-LAYOUT.md:215). If `KB/Permanent` is human-authored, ADR-043 must either amend the ownership rule to make `KB/Permanent` a human-owned exception, or put permanent notes somewhere outside `KB/`. Do not leave this as “obvious from context”; it is a direct ownership drift.

ADR-042 says to preserve `shared/kb_writer.py`, `shared/concept_dispatch.py`, `agents/robin/kb_search.py`, `kb_indexer`, `kb_chunks`, `wikilinks`, and metadata in [docs/decisions/ADR-042-retire-textbook-lane-lighten-kb.md](E:/nakama-adr043-centaur/docs/decisions/ADR-042-retire-textbook-lane-lighten-kb.md:38). ADR-043 changes the semantics of several of those preserved surfaces. That is acceptable, but only if the ADR names the compatibility work. `shared/concept_dispatch.py` still wraps `upsert_concept_page` in [shared/concept_dispatch.py](E:/nakama-adr043-centaur/shared/concept_dispatch.py:1). `kb_indexer` indexes `KB/Wiki/Sources`, `Concepts`, `Entities`, and `KB/Annotations`, but not `KB/Permanent`, in [shared/kb_indexer.py](E:/nakama-adr043-centaur/shared/kb_indexer.py:56). Brook synthesize groups search hits without candidate/permanent distinction in [agents/brook/synthesize/_search.py](E:/nakama-adr043-centaur/agents/brook/synthesize/_search.py:73). Reading Context Package explicitly walks concept pages in [agents/robin/reading_context_package.py](E:/nakama-adr043-centaur/agents/robin/reading_context_package.py:24). Without code changes, candidates remain canonical to consumers and permanent notes remain invisible.

Robin’s `CONTEXT.md` is internally aware of this drift: the new Centaur section says the old Global KB Concept meaning is shifting toward candidate/reference material in [agents/robin/CONTEXT.md](E:/nakama-adr043-centaur/agents/robin/CONTEXT.md:87). That helps, but the older Source Promotion vocabulary remains present above it. ADR-043 should make the vocabulary transition explicit: “Global KB Concept” is deprecated as a canonical term; “Candidate Concept” and “Permanent Note” replace it.

**3 — NUMERICAL / FACTUAL CLAIMS**

The ADR’s KB-size numbers are historical, not current. ADR-042 says the cleanup reduced `KB/Wiki` from 3,324 markdown files to 481 markdown files and 92.5 MB to 60.9 MB in [docs/decisions/ADR-042-retire-textbook-lane-lighten-kb.md](E:/nakama-adr043-centaur/docs/decisions/ADR-042-retire-textbook-lane-lighten-kb.md:49). The live vault now shows `KB/Wiki` at 95 markdown files, about 826 KB, with `KB/Wiki/Concepts` at 0 markdown files. That makes the migration risk much lower than the ADR suggests, but it also means the ADR is partly solving for a concept backlog that no longer exists.

The “200-500 documents / ~100K token” scale brake for LLM-over-small-corpus connection discovery is plausible only under a strict definition of corpus. If each permanent note is short, 200-500 notes can fit into a 100K-token prompt with compact frontmatter and bodies. If the implementation feeds `KB/Wiki/Sources`, annotations, digests, or full candidate concept pages, it will blow past that quickly. The existing search code already warns that LLM reranking hits prompt-token limits above around 50 chunks in [agents/robin/kb_search.py](E:/nakama-adr043-centaur/agents/robin/kb_search.py:151). ADR-043 must define connection discovery as “`KB/Permanent` bodies plus compact metadata only,” and require a token-budget preflight before any all-corpus LLM call.

The methodology’s conceptual scale claim is directionally fine: permanent notes are meant to be the small human-authored corpus, not the raw vault. But ADR-043 must stop treating “small corpus” as self-enforcing. The codebase has no such boundary today. `kb_indexer` does not index `KB/Permanent`; `kb_search` examples still point at `KB/Wiki/Concepts`; Brook consumes whatever search returns. The brake has to be implemented at the corpus selector level.

The PR/N519 claim is accurate: the ADR correctly separates the methodology document from repo reality. The cited PR number is not present as a merged implementation here. The branch exists, but current code remains dry-run for B promotion.

**4 — ASSUMPTION PUSH-BACK**

Claude’s largest assumption is behavioral: that `KB/Permanent` will actually get used. The methodology itself says the permanent note layer only proves itself after an honest multi-month test. ADR-043 should not authorize a broad platform migration before the owner has written enough permanent notes to expose the real workflow. A personal knowledge system fails quietly: folders exist, UI exists, candidates accumulate, and the human-authored layer stays empty. Given the live vault has zero concept pages today, the immediate problem is not “migrate old concepts”; it is “prove 修修 will write permanent notes after reading.”

Make the three-month test a gate, not a footnote. Define pass/fail criteria: number of permanent notes created by hand, number reused in Brook or writing output, number linked from source annotations, and whether the owner voluntarily returns to the layer. If the layer does not get used, delete the planned Bridge expansion instead of preserving it as architecture debt.

The “by-construction light lock, no hash/guard” assumption is philosophically aligned with a personal system, but it is not enforceable as written. “No LLM writes `KB/Permanent`” is only true if all write paths respect it. The code has multiple writer surfaces: `kb_writer`, `concept_dispatch`, promotion rendering/commit, annotation store, and future Bridge actions. Do not add cryptographic hashing or a hard policy engine, but do add light tripwires: tests that promotion target resolution never returns `KB/Permanent`; tests that permanent-note body writes only come from a human-facing command; and an audit grep in CI or dev scripts for `KB/Permanent` write calls. That is still light. Pure convention is just hope.

Demoting C concept pages is also riskier than Claude’s framing. Today, because the concept directory is empty, there is little data to demote. But the code path still writes future Route C concepts as canonical pages, and downstream consumers still treat concepts as search evidence. If ADR-043 changes those pages to candidates, Brook synthesize, `kb_search`, Reading Context Package, and any future source promotion UI need candidate-aware filtering and labels. Otherwise Brook may cite AI drafts as if they were human knowledge, which violates the point of Centaur Zettelkasten.

Do not ship “candidate” as frontmatter only. It has to affect retrieval defaults. The default ranking should prefer `KB/Permanent`; candidates should be opt-in reference material or lower-trust supporting context. If candidate pages remain in the same search lane with no weighting, ADR-043 changes labels but not behavior.

**5 — ALTERNATIVES NOT CONSIDERED**

First alternative: keep LLM concept pages as a reference index and skip `KB/Permanent` for now. This is the most conservative engineering option. The code already supports `KB/Wiki/Concepts`, diff-merge, source maps, annotations, and search. The tradeoff is that it abandons the methodology’s central claim: the human rewriting friction is the knowledge-making step. If 修修 mainly wants better retrieval and synthesis, this alternative is cheaper and more honest. If 修修 wants a true Zettelkasten practice, it is insufficient.

Second alternative: run an Obsidian-first permanent-note pilot with almost no new web UI. Create `KB/Permanent`, a markdown template, an indexer update, and a small command to show source/candidate context while the owner writes in Obsidian. Do not build the full Bridge authoring workflow until the habit is proven. This fits the “keep it light” constraint better than a UI-first plan. The tradeoff is less polish and less immediate integration, but it directly tests the riskiest assumption: whether the human note layer gets used.

Third alternative: sequence E-first instead of C-first. ADR-043 leans C-first because Route C already has LLM concept writing. But video currently has no concept candidate path and already centers human-selected annotations and speaker entities. That makes E a cleaner proving ground for permanent-note creation without the baggage of demoting existing concept semantics. The tradeoff is that E may produce less dense conceptual material than long articles, but it avoids destabilizing C consumers while the permanent layer is still unproven.

A fourth sequencing variant is “retrieval first, writing later”: update `kb_indexer`, `kb_search`, Brook, and RCP to understand `KB/Permanent` and candidate trust levels before changing any ingest writer. This prevents invisible permanent notes and prevents candidates from being treated as canonical. It is less visible than UI work, but it is the correct dependency order.

**6 — FINAL VERDICT**

Approve with modifications. The core architectural direction is sound: human-authored permanent notes should be the canonical knowledge layer, and LLM-generated concept pages should not masquerade as settled understanding. But ADR-043 as written overstates current migration needs, underspecifies consumer compatibility, and relies too much on convention for the human-only boundary.

Top required changes:

1. Replace the Slice 0 migration story with current-state reality. `KB/Wiki/Concepts` exists but has zero markdown files in the live vault. Do not plan a bulk demotion as if hundreds of concept pages exist. Instead, define how future Route C concept outputs become `Candidate Concept` pages.

2. Add a compatibility section for consumers. Update `kb_indexer`, `kb_search`, Brook synthesize, Reading Context Package, `VaultKBConceptIndex`, `promotion_targets`, `promotion_renderer`, and `concept_dispatch`. Permanent notes must be indexed and preferred; candidate concepts must be labeled and lower-trust or opt-in.

3. Amend ownership docs. Either make `KB/Permanent` a documented human-owned exception under `KB/`, or choose a human-owned top-level path. Leaving `KB/` as “Agent only” while adding human-authored notes inside it creates immediate documentation drift.

4. Make the three-month test a hard gate. Do not expand B/E convergence or build a full Bridge authoring system until the owner has proven the permanent-note habit with actual notes and reuse.

5. Add light tripwires, not heavy enforcement. No hashes are needed, but tests should prevent automated writers from targeting `KB/Permanent`, validate candidate schema changes, and enforce token-budget preflight for LLM-over-corpus discovery.

With those changes, ADR-043 becomes a good personal-system architecture. As-is, it is conceptually right but operationally loose.
