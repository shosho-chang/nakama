01

核心原則：摩擦篩選

這套系統的每一條規則，都從一個原則推導出來。先把它講清楚，後面才不會淪為一堆任意的選擇。

傳統筆記法之所以有用，很多時候不是因為「筆記」本身，而是因為製作筆記時你必須克服的摩擦——在克服的過程裡，腦中的神經連結被一條一條地接了起來。如果把克服摩擦這件事整個省掉、全交給 AI，神經連結就沒有機會經由努力而形成。你會得到三百個格式良好、歸類完美、卻完全沒用的檔案。

所以真正的問題，從來不是「要不要用 AI」，而是一條更細的界線：哪些摩擦該留給人、哪些摩擦純粹是損耗，可以交給機器。這兩種摩擦必須分清楚：

兩種摩擦

生產性摩擦（留給人）。這種摩擦本身就是學習在發生。用自己的話改寫一個概念，逼你檢驗有沒有真懂；決定一個想法該連到哪裡，逼你看出關係；判斷某個概念值不值得獨立成卡，逼你提煉本質；發現兩個來源互相矛盾後決定自己信哪邊。這些就是神經連結在努力中形成的時刻。

純損耗摩擦（交給 AI）。這種摩擦不產生任何理解，只是稅。把劃線從 Kindle 搬到筆記軟體、更新交叉引用的連結、檢查格式一致、找出哪些頁沒被連到、把日期戳對齊、定期掃出矛盾。做這些事的時候，你的大腦沒有長出任何新東西。

分辨兩者，只需要問一個問題。這個判準，是整份文件最重要的一句話：

這個動作，如果我親手做，過程中會不會產生一個我原本沒有的判斷或理解？
會 → 留給人。不會、只是把已有的判斷執行出來 → 交給 AI。The Friction-Selection Test ── 本系統的第一性原理

這個判準比「永久筆記由人寫」更好用，因為它能切到單一動作的層級——連永久筆記裡，都有可以拆出去的損耗（例如它的格式化、它的 metadata、它跟舊卡的候選連結清單）。後面所有的分工、所有的紅線、所有交給 Claude Code 的規則，都是這一條的延伸。

一個必須面對的張力

這套系統正面接合兩個看似衝突的傳統。卡片盒（Ahrens／Houmann）的鐵則是「改寫即理解」——改寫這個動作本身就是理解的發生點。Karpathy 的 LLM Wiki 的賣點則是「把記帳外包給不會無聊的 LLM，維護成本歸零」。表面上它們對撞，實際上摩擦篩選原則同時容納了兩者：改寫留給人，記帳交給 AI。衝突只發生在有人想讓 AI 越界、連改寫都代勞的時候——那正是要守住的那條線。

02

歷史脈絡：一部摩擦篩選史

這套方法不是發明，是繼承。用「摩擦篩選」這條線回看整部筆記史，你會發現驚人的連貫：每一代人都在殺掉當時最重的那道損耗摩擦，卻不約而同地保留同一道判斷摩擦。

沒有哪個思想家是抱著「我要篩選摩擦」的念頭在做事——這是事後回看才浮現的一條線。但一旦用這條線去讀，從亞里斯多德到 Karpathy，每個人發明的工具幾乎都是同一件事：把某種機械苦工自動化掉，好騰出心力給真正的思考。

盧曼的那條線，為什麼是地基

德國社會學家 Niklas Luhmann 用一生累積約九萬張卡片，寫出超過七十本書、四百篇論文。他幹掉的，是 commonplace book 和洛克索引共同的死穴：主題分類是僵固的，一個想法只能放進一個抽屜，於是想法之間無法對話。他的解法是原子化、固定編號、用連結取代分類。

但他最重要的貢獻，是把那道不可外包的摩擦明確講出來了。盧曼說沒有書寫就沒有思考；他形容卡片盒是他的「溝通夥伴」，因為連結會逼他看出他原本沒看到的關係。這條線——改寫與連結這道摩擦神聖不可侵犯——被後來七十年的實踐反覆驗證，也正是你現在要守的那條。

Karpathy 接手的，是 Bush 八十年前的難題

Vannevar Bush 在 1945 年想像的 Memex，是史上第一次有人主張連「索引」這種人為分類都太武斷，工具應該模仿人腦的聯想。但他撞上一道那個年代無解的摩擦：誰來維護這些聯想路徑？建立和保持 trails 需要大量人工，他沒有答案。這道摩擦懸了八十年。

你在歷史中的精確位置

Karpathy 的 LLM Wiki 接手的，正是 Bush 點出、卻無人能解的維護摩擦——這是純損耗。而它最大的爭議（qaadika、Jônadas 的批評），恰恰來自有人想讓它越過盧曼那條線、把「改寫與理解」也外包掉。批評者其實是在替盧曼喊話。所以你不是在發明新界線，你是站在盧曼劃下、被七十年驗證的那條線上，只是手上多了一個終於能解決 Bush 維護難題的工具。

03

各學派的精華

這套系統不挑邊站，而是從每位思想家身上拿走他最對的那一塊。以下是我們保留的東西，以及為什麼。

Sönke Ahrens／盧曼 — 改寫即理解

三類筆記（瞬時／文獻／永久）、原子性（一則一個概念）、用連結取代分類。最核心的一句：如果你無法用自己的話簡潔講出來，代表你還沒懂。這是整套系統「永久筆記必須人寫」紅線的源頭。

Tiago Forte — 漸進式摘要

蒸餾不必一次做完。分層處理：原文 → 加粗關鍵 → 高亮精華 → 用自己的話寫重點摘要，而且只做這份資訊值得的程度。這是聰明的摩擦工程——把一次性的大摩擦，攤平成多次近乎免費的小動作。我們用它來分流：高價值書走完整原子化，一次性參考書只做到加粗高亮。

Nick Milo — Maps of Content

MOC 是「活的目錄」，只放指向其他筆記的連結。關鍵威力：一則原子筆記可以被多個 MOC 連結，使同一個概念在多個主題下同時浮現，而不是被埋在某一本書底下。建 MOC 的時機是「心智擠壓點」——當你被筆記數量壓得喘不過氣時。

Christian Houmann — 劃線必寫為什麼

最可照抄的實作紀律：劃線當下一定寫一句「為什麼」，這是防止淺層處理的第一道閘門；處理時刪掉逐字引文、只留少數標竿句，逼自己用自己的話留存。

Andy Matuschak — Evergreen，概念導向

永久筆記要依概念命名，而非書名／來源／時間——這是讓同一概念能跨書合併、不被埋葬的關鍵。筆記應為你思考而寫，不只為記錄你的思考。

Andrej Karpathy — LLM 做維護

把知識當程式碼來「編譯」：來源是原始碼、LLM 是編譯器、wiki 是輸出、lint 是測試。真正的貢獻不是檢索，而是把維護成本壓到近零，讓系統活得過第三個月，知識得以複利累積。我們拿走它的三件事：compile-once 的綜整、lint 一致性健檢、以及 schema 作為紀律核心。

04

系統架構

把 Karpathy 的 raw／wiki／schema 三層，跟卡片盒的文獻／永久／索引筆記一一對映——但把「永久筆記」這一層從 LLM 手裡搶回來。這個對映，就是整套整合的骨架。

LLM Wiki 層對映到筆記學派誰維護理由
raw/　不可變來源原始劃線 ＋ 你的劃線理由你擷取Houmann：劃線必寫為什麼
wiki/sources/　來源摘要頁文獻筆記LLM 編譯本就是綜整，AI 又快又一致
permanent/　概念頁永久筆記＝你的原子卡你寫，AI 唯讀← 這是那條紅線
wiki/index.md ＋ MOC索引筆記／Maps of ContentLLM 維護骨架，你定邊界記帳給 AI，判斷留人
CLAUDE.md　schema你的筆記法則本身你寫schema 才是真正的產品
log.md ＋ lint（卡片盒沒有的新能力）LLM 做AI 帶來的淨增益，純拿

關鍵設計是 permanent/ 與 wiki/ 實體分成兩個資料夾，並在 schema 裡明文規定 LLM 對 permanent/ 只能讀、不能寫。這就是社群一再強調的 vault 分離（個人 vault vs. agent 工作 vault），也是多數失敗案例的根因——他們讓 AI 寫進了該由人寫的那層。

目錄結構
# 一個主題一個 vault；permanent/ 與 wiki/ 實體分離
my-kb/
├── raw/                      # 第一層：不可變來源，git 版控，只進不改
│   └── books/摩擦筆記法/
│       ├── highlights.md     # 劃線 ＋ 每條的「為什麼」
│       └── source.md         # 書目 metadata
├── wiki/                     # 第二層：LLM 擁有，可重建
│   ├── index.md              # 內容目錄（每次 ingest 更新）
│   ├── log.md                # append-only 時間紀錄
│   ├── sources/              # 文獻筆記（附 citation 回 raw/）
│   ├── concept-candidates/   # AI 概念候選，標 #ai-draft
│   └── moc/                  # Maps of Content
├── fleeting/                 # 瞬時筆記收件匣（見「瞬時筆記」一節）
├── permanent/                # 第三層：你的卡片盒，AI 唯讀，絕不寫入
│   └── 延遲折現偏誤.md
└── CLAUDE.md                 # schema＝筆記憲法

05

資料夾與檔案的實際長相

架構講的是「為什麼這樣分層」，這一節講「實際打開資料夾會看到什麼」。以你的三種來源——EPUB 電子書、plugin 抓進來的網路文章、邊看邊標的 YouTube 逐字稿——為例，逐檔說明。

先看完整的頂層樹。比起前面的架構，這裡多了一個 fleeting/（瞬時筆記收件匣，下一節詳談），以及 raw/ 內依來源類型分的子資料夾：

完整頂層結構
my-kb/
├── raw/                          # 不可變來源 · 你策展 · AI 唯讀
│   ├── books/                    # EPUB 電子書
│   ├── articles/                 # plugin 抓進來的網路文章
│   └── videos/                   # YouTube 逐字稿 + 你的標註
├── fleeting/                     # 瞬時筆記收件匣 · 會被定期清空
│   └── inbox.md
├── wiki/                         # LLM 擁有 · 可重建
│   ├── index.md
│   ├── log.md
│   ├── sources/
│   ├── concept-candidates/
│   └── moc/
├── permanent/                    # 你的原子卡 · AI 絕不寫入
└── CLAUDE.md

raw/ ── 每個來源資料夾裡放兩個檔

原則很簡單：純淨原文一個檔、你的閱讀標註一個檔，分開放。原文不可變、可被 AI 引用；標註是你的話、是理解的種子。你列的那 4 件事，就分布在這兩個檔裡：

你的 4 件事 → 各自存在哪

① Raw 原檔 → source.md（書／文章）或 transcript.md（影片）。純文字，不可變。EPUB 額外保留原始 .epub，並抽一份純文字供 AI 讀取與引用；內嵌圖片本地下載。

② Highlight、③ Annotation、④ 章末心得 → 全部放同一個 highlights.md：劃線用引用區塊、註解寫在它下方、章末心得放在章節標題尾。

關鍵概念：②③④ 都是「你的話、capture 等級的 literature 材料」，所以它們屬於 raw/——是你不可變的閱讀紀錄。AI 只讀、不改寫它們。wiki/sources/ 是 AI 從它們編出的 digest。兩者都還不是 permanent 卡——永久卡是你接下來親手寫的原子概念。

raw/books/ ── EPUB 電子書
raw/books/深度工作/
├── 深度工作.epub          # 原始檔，保留
├── source.md              # 抽出的純文字（含錨點），AI 讀這個
└── highlights.md          # 你的劃線 + 註解 + 章末心得

打開上面那個 highlights.md，就會看到你的 ②③④ 全裝在同一個檔裡——劃線用引用區塊、註解接在下方、章末心得放在章節尾：

highlights.md ── 同時裝下你的 ②③④（這就是 literature 材料）
---
source: books/深度工作
type: book
status: captured        # captured → digested → mined
captured: 2026-06-01
---

> 高品質工作產出 = 時間 × 專注強度  ^loc-203      # ② Highlight + 錨點
why:: 這條公式可直接套在我的內容產出上。       # ③ Annotation

> 網路工具正在削弱我們深度工作的能力  ^loc-142

### 章末心得                              # ④ 一整章看完的感想
這章讓我重看自己的 YouTube 流程，其實淺工作占太多……

那兩個 ^loc-203 是 Obsidian 的區塊錨點，讓 AI 能精準把每個宣稱引用回原文的確切位置——這是「強制 citation」紅線能落地的技術前提。三種來源的錨點各有對應：

raw/articles/ ── plugin 抓進來的文章
raw/articles/2026-05-pg-how-to-think/
├── source.md       # plugin 抓的正文（frontmatter 存 url/作者/擷取日）
└── highlights.md   # 同上結構；錨點用段落 ^p-12

影片來源結構一樣，只是用逐字稿取代原文，錨點改成時間戳：

raw/videos/ ── YouTube 逐字稿 + 邊看邊標
raw/videos/2026-06-huberman-sleep/
├── transcript.md   # 逐字稿，每段帶時間碼
└── highlights.md   # 你標的句子 + note；錨點用時間戳 ^t-1432
影片來源的小紅利

影片 highlight 的錨點用時間戳（^t-1432 = 第 1432 秒）。於是 AI 在 wiki/sources/ 引用某個宣稱時，可以直接連回「影片的那一刻」——這是純文字來源沒有的精準溯源。你的 plugin 之後也可以把這個時間戳變成可點的 YouTube 連結。

wiki/ ── 由 LLM 維護，每個檔各司其職

這是你最想搞清楚的一欄。wiki/ 裡沒有「你的原創想法」——那些在 permanent/。wiki/ 裝的是 AI 對你 raw/ 的綜整、索引與健檢。各檔作用如下：

檔案作用誰寫
index.md內容總目錄。讓 agent 少讀整檔就知道有什麼；也是你的儀表板AI
log.mdappend-only 時間軸，grep 友善，記錄每次 ingest／lintAI
sources/{名}.md文獻摘要 digest，每個宣稱附 citation 回 raw/AI
concept-candidates/{名}.draft.md概念候選鷹架，給你改寫，一律標 #ai-draftAI
moc/{主題}.md活的目錄，只放連結；一張卡可入多個 MOCAI 維護骨架／你定邊界

瞬時筆記 Fleeting Notes 如何接入

前面的流程都從「一個來源」開始。但最好的想法常常不附在任何來源上——洗澡時、跑步時、講話講到一半冒出來的火花。這一節補上卡片盒的這塊：瞬時筆記怎麼進系統、怎麼跟系統互動。

瞬時筆記跟前面所有東西的根本差別是：它不是來源材料，也還不是永久卡，而是一顆「種子」。它已經是你自己的話（你寫的），所以它是永久卡的種子，不是 raw/ 的素材。Ahrens 對瞬時筆記的鐵則只有一條——捕捉的摩擦要降到最低，因為火花稍縱即逝；至於整理，是之後的事。

fleeting/inbox.md ── 最低摩擦，一行一則
# Fleeting Inbox

- [2026-06-05 07:12] 摩擦篩選會不會也適用在「運動訓練」？
  痛苦=生產性摩擦，受傷=損耗摩擦。可能是一支影片。
- [2026-06-05 14:30] 標題靈感：「你的筆記為什麼是死的」
- [2026-06-04 22:01] Huberman 講的睡眠時數，跟我上週讀的那本書好像矛盾

關鍵在捕捉與整理分離。捕捉時什麼都別管，丟進 inbox 就好（手機上用 Obsidian 快速捕捉、甚至語音轉文字都行）。整理是定期（例如每週）做一次 triage，這時才動腦——而 AI 在這裡扮演「協助你看見關聯」的角色，但不替你做決定。

瞬時筆記與系統的三種交互

注意那四個去處裡，有三個會「回饋」進系統，讓火花不白費：

  • 變成永久卡（最有價值）。一個值得發展的火花，由你親手寫成 permanent/ 的原子卡。火花是種子，把它長成能獨立站立、能連結的完整概念，就是思考發生的地方——所以這步是紅線，AI 不代寫。
  • 變成研究問題、觸發攝入。有些火花是「我需要查證的假設」（例如上面那條睡眠時數的矛盾）。它就轉成一個研究問題，讓你去找來源、跑 /ingest。瞬時筆記在這裡成了 raw/ 的觸發器。
  • 變成連結或選題。有些火花本身就是「我發現 A 跟 B 有關」。它的歸宿是一條連結、或 MOC 上的一個開放問題、或你的下一篇選題——這正好接上輸出複利閉環。
給 CLAUDE.md 的新增條款

/triage-fleeting 指令：讀 fleeting/inbox.md，對每一則火花，列出它與既有 permanent/ 卡及 wiki/sources/ 的可能關聯，並建議處置（丟棄／發展成卡／需找來源／連結）。但不替使用者改寫成永久卡、不自動刪除任何一則。使用者處理完一則，就把它從 inbox 移除。AI 對 fleeting/ 可讀、可建議，但不得自行清空或改寫內容。

這樣，瞬時筆記就完整接進系統了：它用最低摩擦進來（保護你不漏掉火花），用人工 triage 出去（保護那道「發展即思考」的生產性摩擦），而 AI 只在中間做它最擅長、也最無害的事——幫你看見「這顆火花跟你已經知道的東西，有什麼關係」。

人機分工界線

把第一性原理落成一張清單。左欄交給 AI，右欄留給你——分界就是那個判準：這個動作會不會產生新的判斷或理解。

三條人類保留紅線

紅線一｜改寫成永久筆記。AI 只能在 concept-candidates/ 提出候選並標 #ai-draft，把候選改寫成 permanent/ 原子卡的那一筆，必須你親手寫。寫不出來，就代表這個概念還不該進卡片盒。

紅線二｜採納並寫下連結。AI 可以「建議」相關筆記，但採納哪條、以及寫下關係說明（支持／矛盾／延伸），是你的判斷——那正是連結產生洞見的地方。

紅線三｜事實回溯查核。wiki/sources/ 每個事實宣稱都要有 inline citation 連回 raw/ 的具體位置。這是對抗「假性連貫（false coherence）」的第一道防線：讓整個 wiki 永遠可重建、可稽核。

08

完整工作流

把六階段管線跟 LLM Wiki 的三操作（ingest／query／lint）疊起來。一本書怎麼從劃線，跑到可複利的永久卡。

把 lint 當研究引擎，不是當雜務

這是 LLM Wiki 對傳統卡片盒最大的淨增益、且零哲學風險——卡片盒從來無法大規模做一致性檢查。對深度研究內容特別有價值：讓 AI 定期掃出「不同來源對同一機制的矛盾說法」，那幾乎就是現成的選題。傳統做法做不到，是因為沒有人能定期把幾百張卡通讀一遍；現在 AI 可以。

viii.
09

輸出複利閉環

最好的學習是輸出。當你能把不同概念連起來、親手寫成一篇有原創洞見的文章，你對主題的理解才真正更上一層。這一節回答：文章寫完後，如何讓它本身回流成系統的新養分——而這是整套理論裡，前人只做到雛形的一環。

盧曼早就把「輸出」當成系統的終點，不是副產品——他的卡片盒就是設計來讓「一篇完成的作品作為做筆記過程的一部分而浮現」。但他講的是 notes → output（文章從卡片長出來）。你要問的是反方向：output → notes，文章寫完了，怎麼回流。傳統方法甚至叫你把專案產物丟掉——因為在紙本時代，為剛寫完的文章再做一份筆記是純損耗。

但摩擦篩選原則給了新答案：當 AI 把回流的記帳摩擦降到近零，「輸出複利閉環」第一次在工程上可行。你不是跟盧曼唱反調，你是接通他當年因摩擦太高而被迫放棄的那條路。文章寫完後，分三路回流：

這件事有人做過嗎？精準定位你的原創

  • 「文章從筆記長出來」(notes → output)：盧曼做到極致，完全不是新的，不必宣稱原創。
  • 「寫作過程萃取新洞見、沉澱回卡片」(output → 新筆記)：傳統方法有雛形，但從沒當成正式步驟教，還叫你把專案產物丟掉。你把它提升為一個明確、必做的步驟，是把隱性知識顯性化。
  • 「把成品文章本身當一等來源、用 AI 近零成本回流，形成自動閉環」：這個我找不到有人系統化提出過。傳統方法因記帳太貴而丟掉文章；LLM Wiki 那邊忙著攝入外部來源，沒人討論攝入你自己的原創輸出。把「輸出」從系統的終點，重新定義成品質最高的新輸入源——這個重新框定是你的。
一個必須守的風險邊界

如果你把②做得太積極——讓 AI 把你所有輸出都自動攝入——你會稀釋掉①。因為你會開始倚賴「反正 AI 會把我的文章編進去」，而省掉「親手拆出新洞見」那一步。閉環的價值完全押在①上；②③只是讓①的成果能被未來取用的管道。所以 /reflux 指令的設計鐵則是：強制先完成①的人工萃取，才觸發②的 AI 攝入。

給 Claude Code 的實作規格

以下是可直接落地的部分：schema 紅線、四個 slash command 的行為定義、規模煞車。隨附的 CLAUDE.md 檔可直接放進 KB repo 根目錄。

啟動：交給 Claude Code 的第一個 prompt

starter prompt
我要在這個目錄建立一套「AI 增強的卡片盒」知識系統。在你做任何事之前：

1. 先讀我附上的方法論（本文件），特別是「人機分工界線」與
   「輸出複利閉環」兩節。
2. 問我這個 vault 的主題是什麼、我打算餵它哪些來源。
3. 等我回答後，依我的回答產生一份客製的 CLAUDE.md（以下方
   範本為基礎），並初始化 raw/ wiki/ permanent/ 的資料夾骨架、
   空的 index.md 與 log.md。
4. 不要在我確認 CLAUDE.md 之前 ingest 任何東西。

CLAUDE.md 的不可違反條款

這份 schema 是整套系統的靈魂，直接決定它變成「理解複利機」還是「三百個沒用的檔案」。以下六條是硬規則：

  1. permanent/ 對你（AI）唯讀。永遠不得在此資料夾建立或修改檔案，只能讀取，並「在別處」提出建議。
  2. raw/ 不可變。只新增、不修改、不刪除；每次 ingest 前先確認 raw 完整。
  3. 強制 inline citation。wiki/sources/ 每個事實宣稱都要連回 raw/ 的具體位置，讓 wiki 永遠可重建、可稽核。
  4. 概念只出候選，不出成品。ingest 時把概念寫進 concept-candidates/ 並標 #ai-draft，絕不直接寫進 permanent/。
  5. lint 是功能不是雜務。每 10–20 個來源跑一次，輸出當「主動研究建議」呈現，不是當待辦清單。
  6. 規模煞車。當 wiki/ 接近 10 萬 tokens／數百頁，停下提醒考慮 hybrid retrieval，不要默默繼續長大。

四個 slash command 的行為

指令做什麼觸及範圍 / 紅線
/ingest讀 raw/ 新來源 → 編 wiki/sources/ 文獻筆記（附 citation）→ 更新 index、log → 丟出概念候選到 concept-candidates/單一來源通常觸及 5–15 頁；絕不寫 permanent/
/lint掃全 vault：矛盾、過時宣稱、孤兒頁、缺失交叉引用、知識缺口 → 輸出成研究建議清單唯讀分析；不自動修改，修法由你決定
/reflux輸出複利閉環：先要求你確認已親手把新洞見寫進 permanent/，才把成品文章收進 raw/、編文獻筆記、列出與舊卡的新連結與矛盾順序鎖：人工萃取（①）未完成則拒絕執行②
/process-inbox把 raw/inbox/ 的零散想法分類、建議歸屬，但只移動、不改寫內容分類建議；採納由你確認
為什麼 Obsidian 只是唯讀檢視器

所有寫入都經 Claude Code，Obsidian 只用來「看」wiki 的形狀（graph view）、讀你的 permanent/。鐵則：不在 Obsidian 直接編輯 wiki/ 頁，因為那會繞過 schema 的約束與 git 的版控。你唯一該在編輯器裡親手寫的，是 permanent/ 的原子卡——而那本來就是你的工作。

Nakama 現況與改造路徑

把前面的方法論，套到你實際在跑的 Nakama 三條 ingest pipeline（B 書、C 文章、E YouTube）。先說結論：這不是打掉重練，而是「重新指向」——你的地基意外地穩，缺的是最關鍵那一層，外加一條走錯了方向。

你目前三條 pipeline 已經有方法論要求的大半基礎設施：不可變的 KB/Raw、畫線存在 KB/Annotations、證據錨點（書的 claim 證據、影片的時間戳）、HITL 審查閘門、atomic write 加備份與 hash。真正缺的，是「永久筆記＝你的話」這一層——而且其中一條（C 文章）還走錯了方向：它的概念頁是 LLM 代筆的。

三條 pipeline 現在停在哪

逐條看：B 書的 claim 抽取還停在 dry-run 佔位（concept 永遠 0），真正的 LLM 抽取器存在卻沒接線（在 PR #833）；它連「概念候選」都還沒真的產出。C 文章是唯一有概念層的，但概念頁由 LLM 寫、還用 Opus 自動 merge——這是錯層不是缺層。E YouTube 其實最乾淨（畫線即證據、零 LLM），但概念層完全 deferred。

最關鍵的一個轉變

核准式 HITL ≠ 作者式 HITL。你現在的人類介入是「核准／勾選 AI 的產出」（B 逐項 approve、C 勾選要執行哪些 concept）。但方法論要的 HITL 是「你親手寫」。核准 AI 寫的東西不會在你腦中形成神經連結，那只是 approval，不是 authorship。整個改造的核心，就是把這一步從「核准」換成「書寫」。

目標：三條收斂成一條共用脊椎

三條的差別只在「證據怎麼來」——B 用 LLM 抽 claim、C 用 LLM 摘要、E 用你的畫線本身。一旦證據到手，三條就該走同一條脊椎，不再各搞各的：

分階段改造

  1. Phase 0 — 清理與骨架（最便宜，先做）。建空的 KB/permanent/、KB/Wiki/MOCs/、KB/Fleeting/inbox.md；把 E 的輸出路徑併入 KB/Wiki/Sources/；把 KB/Wiki/Concepts/ 現有頁標記 status: candidate + #ai-draft（先別刪，當待升級的候選）。
  2. Phase 1 — 基石：加入「人親手寫」這一步。做一個「候選 → 永久」的升級介面：顯示 AI 概念候選＋證據＋建議連結，但讓你打字寫出自己的話，存到 KB/permanent/{concept}.md 並附 citation 回 source／annotation。順序鎖：AI 永不寫 KB/permanent/，且升級時系統要求你輸入的文字與候選不同（不能直接複製候選）。
  3. Phase 2 — 三條收斂到脊椎。B：接上真 LLM claim 抽取器（PR #833），但輸出導到「概念候選」而非自動 concept，順手修三個切章 bug（過濾致謝／版權頁、reason 取章節論點而非 claims[0]、include 門檻收緊）。C：停止把概念頁當成品自動寫入與 Opus 自動 merge，改成產出候選；永久筆記由你在 Phase 1 介面寫；Entities 維持 AI 參考。E：把畫線叢集餵給候選產生器，再由你寫成永久筆記。
  4. Phase 3 — 維護與複利。AI 維護 KB/Wiki/MOCs/ 骨架、把永久筆記掛進對應 MOC（建議連結、你確認關係）；新增 /lint（你現在三條都沒有！）做跨來源矛盾偵測→當研究選題；接上 fleeting inbox＋triage；最後接輸出複利閉環 /reflux。

上手路徑與自我檢驗

不要一開始就上重型基礎設施。分三階段，每階段標出「該往下一階段走」的訊號。

階段一 — 試水溫（個人規模）

拿一本你真的讀透的書，跑完整流程，先針對「一個」聚焦主題、5–20 個來源做。把 Obsidian 當唯讀檢視器，所有寫入經 agent。門檻：只要 wiki 還在約 10 萬 tokens／數百頁以內，純 markdown ＋ index 就夠，不要過早上 RAG／向量庫——那違背 Karpathy「無基礎設施」的初衷。

階段二 — 嚴肅使用（建立紀律）

把三件事當第一級操作：強制 inline citation 回 raw/；每 10–20 個來源跑一次 /lint 並把結果當研究建議；raw/ 嚴格不可變、用 git 版控。團隊使用則考慮 per-file locking 與「人類審查為寫入閘門」。

階段三 — 規模化訊號

當 wiki 開始出現重複頁、矛盾、檢索漂移（通常在約 200–500 文件／200K–300K tokens），這是改用 hybrid 的訊號：核心穩定知識留 context，動態海量資料接向量檢索；再考慮 typed relationships 與 confidence scoring。

三個月後的誠實測試

跑一陣子後，做一個誠實的自我測試：三個月後，permanent/ 裡你親手寫的卡，跟 wiki/sources/ 裡 AI 編的摘要，哪一個你還記得、還用得上？

如果是前者——這套分層就值得，你守住了那條線。如果你發現自己根本不看 permanent/、只查 wiki，那代表你要的其實只是個可查詢的參考索引，別假裝在做卡片盒，直接用純 Karpathy 版省事。這套系統的賭注是：省下執行的摩擦，換來你有餘力去做更多判斷的摩擦。如果省下時間後你連改寫都想叫 AI 代勞，就會滑回三百個沒用檔案的下場。紀律不在 schema 寫得多嚴，而在你守不守得住第③步那條線。

附錄：原創歸屬與限制

為了讓這套方法經得起別人追問「這是你自己想的還是別人講過的」，誠實標出哪些是繼承、哪些是你的綜合。

哪些是前人既有

  • 改寫即理解、原子化、連結即思考——Ahrens／盧曼，並有認知科學背書（Bjork 的 desirable difficulties：自己 generate 答案比被給予更能形成長期記憶）。
  • 分層蒸餾、為未來的你設計筆記——Tiago Forte。
  • MOC、一卡多連——Nick Milo。
  • LLM 做維護、lint、compile-once、schema 為核心——Karpathy 與其社群。
  • 「某些 grunt work 是價值來源、不該外包」——HN 使用者 qaadika 的單點反駁；Jônadas Techio 的「未經治理的編譯器不會思考，它只會撫平」。

哪些是你的綜合

  • 「摩擦篩選」作為統整框架——用「保留生產性摩擦、消除損耗摩擦」這條線回看整部筆記史。構成它的磚（Bjork、qaadika、Forte 的摩擦工程）各自存在，但把它們疊起來、鋪成歷史主軸，找不到先例。這是一個原創的詮釋視角，不是新發現的事實——定位要誠實，但它站得住腳。
  • 「輸出複利閉環」——把成品文章本身當一等來源、用 AI 近零成本回流，並把這道在紙本時代純損耗、故被盧曼放棄的路徑，重新接通成自動閉環。把「輸出」從系統終點重新定義為品質最高的新輸入源，這個重新框定是你的。
  • 把 raw／wiki／permanent 的 vault 分離，明確對映到「人機分工紅線」——讓 Karpathy 的工程架構與盧曼的認識論紅線在同一張資料夾結構裡共存。

限制與不確定性

  • 術語不通用：fleeting／permanent、CODE、evergreen 各家命名衝突，本系統已自訂明確定義，勿假設與他人共通。
  • 規模相依：同一模式在 100 頁是「驚艷」、在 2,000 頁可能「沒人編輯的垃圾場」。多數失敗根因不是模式本身，而是跳過了 lint、溯源、vault 分離這幾項紀律。
  • 量化宣稱多為軼事：社群流傳的「95% token 下降」「17% 連貫性差距」等數字無公開方法學，不應當作驗證過的基準。
  • AI 立場非一面倒：社群中既有「人類保留理解」的主流，也有積極用 LLM 加速的少數派；本系統選擇前者，是價值選擇，不是經驗定論。
