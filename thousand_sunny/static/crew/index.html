00 nakama · ai crew setup

八個 AI 船員的內容團隊
一個創作者、八個船員、兩台機器、一艘船

Nakama 是張修修的個人成長內容生產 AI Agent 系統 — 主題橫跨長壽健康、生產力、心理學、創業與財務，並製作人物專訪 podcast。船員以《航海王》草帽團命名，每位船員的職務對應他的運算角色：考古學家管知識庫、航海士當秘書、劍士做關鍵字偵察、船匠顧系統。部署在一台 VPS 上，產出雙向同步回本機的 Obsidian LifeOS。這頁把整套 setup 攤開：船員分工、七層內容流程、每日排程、操作原則、runtime policy。

命名梗：船長是修修本人，Thousand Sunny（千陽號）是承載全員的平台（web server / 甲板儀表板），不是船員。狀態標誠實標示 — shipped / in-dev / planned 各如其實。

02content pipeline

內容流程七層

任何「開發 X」對話都必先 anchor 在某個 stage，不可 spontaneous 開發。原料從外部世界進來，一路走到發布，理想上 Stage 7 的成效要回灌 Stage 1。

  1. 1 收集 Discovery 趨勢 / 文獻 / 新聞 / 社群 → 原料素材 Zoro · Franky · Robin
  2. 2 閱讀 + 註記 Reader 雙語閱讀 · 劃線 + 筆記 + reading session Robin
  3. 3 整合 Ingest 原料 + 註記 → KB Wiki（Source / Concept / Entity） Robin · Brook
  4. 4 原子文章 canonical content：手寫心得 / 字幕檔 / LLM 輔助稿 — LLM 不代寫正文 修修 · transcribe · Brook scaffold
  5. 5 製作 Production fan out 4 channel：影片 / 部落格 / FB / IG Brook · Foundry
  6. 6 發布 Publishing 上線到各平台 · 目前僅 WP 自動，YT/IG/FB 缺口 Usopp
  7. 7 監控 Optimization analytics → SEO 分數 / 排名 / 回饋 → 回灌 Stage 1 Brook · Franky
結構性觀察 #1 Stage 7 → Stage 1 閉環目前是斷的
Zoro 偵察 → 人肉橋接 → Robin / Brook 寫 → 人肉發布 → SEO 中控台 audit → 回不去 Zoro。內容效能無法 inform 下次選題，每集從零開始。誠實標示，不假裝閉環已成。

04operating principles

操作原則

讓人放心把工作丟出去的先決條件。少了任何一條，自動化都會在某個地方漏。

三條紅線

任何任務共同遵守

  1. 閉環意識 — 每個任務有明確 Definition of Done，「差不多了」不算完成
  2. 事實驅動 — 每個判斷附檔案路徑 + 行號，「我猜」「應該是」是違規
  3. 窮盡一切 — 清單不跳過，乾淨的項目明確標「已檢查無問題」，不靜默忽略
模式切換

依任務規模換檔

  1. P7 執行 — 單一功能：讀現狀 → 方案 → 影響分析 → 實施 → 三問自審
  2. P9 規劃 — 3+ 檔：拆六要素 Task Prompt，輸出是 prompt 不是 code
  3. P10 戰略 — 跨服務：輸出目標 / 指標 / 風險 / 時程戰略文件
工作面紀律

control plane ≠ write surface

  1. 主倉庫只允許讀 / fetch / pull --ff-only / 開 worktree / merge
  2. 每個 task 開 sibling worktree 改檔，memory 永遠不在主倉庫寫
  3. 禁 git add . — 只 stage 明確列出的 path，避免混入無關改動
記憶寫入

三層觸發紀律

  1. L1 明確 — 使用者說「記下 / save」→ 立即寫 durable memory
  2. L2 強訊號 — 明確 correction / validation / 新穩定事實 → 寫 durable
  3. L3 session 邊界 — 「收工 / 對話結束」→ 寫 ephemeral handoff，不污染 git
美學 first-class

不是 nice-to-have

  1. 所有 UI surface 出手前讀 design-system.md，走單一 --sho-* token
  2. 拒 AI slop：無 Inter/Roboto、無紫漸層、無均勻 card grid 當預設
  3. 每個 state（hover / focus / empty / error…）都設計過，a11y 不妥協
multi-agent

Claude + Codex 協作

  1. 記憶按 agent + 語言切：Claude 讀寫 claude/、Codex 讀寫 codex/
  2. shared/ 強制 bilingual frontmatter，否則跨語言找不到
  3. UPDATE 走 .lock，衝突絕不 silent last-write-wins，必呼叫使用者
Sandcastle default

並行 dispatch 走雲端隔離

  1. Default 用 Sandcastle（cloud isolation）跑並行 / AFK 任務
  2. 本機 isolation: worktree 只用於能盯住全程的單一短任務
  3. backend → Sandcastle、UI → 主 session（瀏覽器驗證在 scope 內）
05runtime policy

Runtime Policy

Nakama 不用 PreToolUse / PostToolUse hook，而是用 .claude/settings.json 的 allow / deny permission list + worktree 隔離當護欄。三類守則：安全、穩定、方便。

／ 01　Security · 安全

destructive 指令一律 deny

下列 pattern 在 settings.json deny list，連明確口頭授權都擋得住 — 要繞過得改 settings 或自己另開 shell 跑。

  • rm · rmdir — 防誤刪（改走回收桶）
  • sudo — 防本機提權
  • git reset --hard · checkout -- · clean — 防 destructive git 丟失未提交
  • Edit(.env) — 防 API key 進 transcript / git
  • scp · rsync — 防檔案外流
／ 02　Reliability · 穩定

主倉庫不可被污染

多視窗並行下，最大風險是 unrelated 改動混進 PR、或主倉庫被 destructive 操作弄亂。

  • 主倉庫只 pull --ff-only，不在上面 checkout 工作 branch
  • 每個 task 開 sibling worktree 隔離 write surface
  • memory commit 走 paths-ignore 直 push main，絕不在 feature branch
  • stash 用 -m 命名，不用 pop stash@{0}（index 會漂移）
／ 03　Convenience · 方便

安全的逃生門

擋掉危險指令之後，留幾條被 allow-list 過的安全替代，讓日常不卡關。

  • 刪檔走 PowerShell 回收桶 DeleteFile(…'SendToRecycleBin')
  • VPS 維運：ssh nakama-vps "journalctl / systemctl …" 已 allow
  • Python / pytest / ruff / git 讀寫全套 allow-listed，不用每次問
